## 验证方法

在本课目录执行：

```powershell
python .\verify.py
```

脚本执行以下有明确目的的检查：

1. 核对完整学习包恰有五部分、十题和十份完整 C 代码；拆分章节与源文件必须和学习包保持一致。
2. 使用 `gcc -std=c11 -Wall -Wextra` 编译十份代码，另加关闭诊断颜色的选项以稳定保存日志；正常示例与两个确定性逻辑错误程序应无诊断。
3. 运行四个实验、三个可安全执行的找错程序和两个设计题实现，检查退出码、断言及预期输出；涉及实现的大小关系从实验 1 测量值推导。
4. 确认数组形参求大小、返回局部地址两个反例会产生相应 GCC 警告；悬空指针程序只编译，不执行。
5. 从 `const` 实验分别生成三个临时变体，确认非法赋值被编译器以只读赋值诊断拒绝；原实验源文件不改动。
6. 以 `-O2` 再运行易变读取实验，并用 `-S` 生成汇编。在本机 x86-64 MinGW 目标上，检查普通函数的一次内存读取与易变函数的两次内存读取；不据此推断其它架构或实际总线事务。
7. 检查本地文档链接，保存文件 hash、完整命令与结果。每次运行建立独立的 `verification/<时间戳>/` 目录，保留失败记录。

首次从完整学习包生成缺少的章节/源文件可使用 `python .\verify.py --materialize`；它不会覆盖已有但不同的文件。练习时建议另存副本：默认验证会报告原文件与讲义不一致，以免把个人改写误当成已验版本。

首轮验证的十份 C 程序编译与九份安全程序运行均通过，但汇编观察器仅统计 `mov`，漏掉了 `addl observed_value(%rip), %eax` 中的第二次内存读取，因而标记为失败。核对实际函数体后，观察器改为识别带相应内存源操作数的 `mov` 和 `add`；C 程序未为迁就检查而改动，原失败记录保留。

## 允许与不允许的结论

最新 JSON 为 `passed` 时，可以说本机已通过上述编译、输出和一致性检查。GCC 版本、目标三元组、`CHAR_BIT`、`sizeof(int)`、对象指针大小以及汇编观察均在详细记录中保留。

这些检查不等于证明任意调用者输入安全，不证明所有 C 实现的行为，不证明任何真实 Cortex-M 外设正确工作，也不证明本地调度器已经恢复。学习包已提供内容，远端调度生成与标准原 PDF 复核仍有上述明确限制。
