### 任务 1.1 · 搞懂三个区（1.5 小时）

```bash

git commit -m "first"         # 本地仓库
echo "more" >> a.txt          # 再改工作区

# 3) 看清楚它在哪一步
git status                    # 告诉你在哪个区
git diff                      # 工作区 vs 暂存区
git diff --cached             # 暂存区 vs 上次提交
git log --oneline --graph
```

**验收**：你能不看笔记回答 —— "改了一个文件没 add 就 commit，会提交什么？"

### 任务 1.2 · 提交信息与撤销（1.5 小时）

```bash
git commit --amend -m "改过的说明"   # 改上一次提交
git restore --staged a.txt           # 只撤销暂存
git restore a.txt                    # 连工作区一起撤销（危险）
git revert <sha>                     # 用新提交撤销旧提交（协作安全）
git reflog                            # 后悔药：找回"删掉"的提交
```

> ⭐ **必须理解 `revert` 和 `reset` 的区别**：
> `reset` 改历史（**只有你能改，别人拉你的分支会出事**），
> `revert` 加一个新提交（**所有人都安全**）。
> 这是"AI 帮你提交"时最容易翻车的地方。

### 任务 1.4 · 关联到你的真实项目（1.5 小时）

把 `D:\RectSSL_AIRD_Quality_20261027_v4\agentrouter_switch_20261109` 变成一个真正的 git 仓库。

> ⚠️ **顺序不能错：先写 `.gitignore` → 再 `git add` → 再扫暂存区 → 才 commit。**
> 顺序反了就要 `git rm --cached` + 改历史，而历史一旦推上去就收不回来。

```bash
cd "/d/RectSSL_AIRD_Quality_20261027_v4/agentrouter_switch_20261109"

# ① 先看这个目录里有什么（有没有已经在 git 仓库里）
git rev-parse --show-toplevel          # 报错 = 不是仓库
ls -A1

# ② ★ 先扫一遍哪些文件真的带凭据（只看文件名，不打印内容）
grep -rIl -E "sk-[A-Za-z0-9_\-]{16,}|gho_[A-Za-z0-9]{16,}|bearer_token|api[_-]?key[\"']?\s*[:=]" . 2>/dev/null

# ③ 写 .gitignore（凭据、备份、运行时、缓存）
#    然后才是 git init / git add -A

# ④ ★ 扫暂存区（这一步比第②步更重要：只看工作区会漏）
git add -A
git ls-files --cached | while read -r f; do
  git show ":$f" | grep -Iq -E "sk-[A-Za-z0-9_\-]{16,}|gho_[A-Za-z0-9]{16,}" && echo "⚠️ $f"
done

# ⑤ 确认该排除的都排除了
git ls-files --cached | grep -E "credentials|switch_backups|pending_state" # 应该是空的

# ⑥ 提交
git commit -m "chore: 初始提交：中转站切换工具与配置"
```

> ⭐ **第 ④ 步是本周最有价值的一条**：它检查的是**将要进历史的内容**，
> 而不只是磁盘上的内容。而且你会发现——
> **扫描器命中 ≠ 泄露**：这个仓库里 6 个文件命中，全是**代码在处理 token**
> （`experimental_bearer_token` 是 config.toml 的**键名**，
> 值是运行时从别处读的；文档里是 `<该站自己的 key>` 这种占位符）。
> **必须逐条看命中行，区分"代码引用键名"和"代码里写着值"。**

**顺带加一个 `.gitattributes`**（把行尾规则钉进仓库，不依赖全局 `core.autocrlf`）：

```gitattributes
*.cmd    text eol=crlf      # cmd.exe 需要 CRLF
*.bat    text eol=crlf
*.ps1    text eol=crlf
*.py     text eol=lf
*.md     text eol=lf
*.json   text eol=lf
*.txt    text eol=lf
*.png    binary
```

> 💡 **Git 不转码，只动行尾**（CR/LF 是 ASCII 字节）⇒ **GBK 中文内容不会被破坏**。
> 你的 `.cmd` 全是 **GBK**（cmd.exe 下中文正常）；`.ps1` 有中文的那个带 **BOM**，
> 其余是纯 ASCII（不需要 BOM）。这两条都可以用一条脚本自检：
> ```python
> b = path.read_bytes()
> bom = b[:3] == b'\xef\xbb\xbf'
> crlf = b.count(b'\r\n'); lf = b.count(b'\n') - crlf
> nonascii = any(x > 127 for x in b)
> ```
> 判定：`.cmd` 有中文 ⇒ 必须 GBK 且 CRLF；`.ps1` 有中文 ⇒ 必须 BOM。

> ⚠️ **注意**：这台机器上还有 `D:\DeepTutorLab`（有 40MB 的 zip 备份和 API key），
> **不要 `git add -A` 把它整个提交上去**。先写 `.gitignore`，再 add。

## 第 2 周 · A2 · 分支与协作（6 小时）

### 任务 2.1 · 分支的真相（1.5 小时）

```bash
git switch -c feature/relay-switch      # 新分支
git switch main                          # 切回去
git branch -a                            # 列出所有
git log --oneline --graph --all
git merge feature/relay-switch           # 合并
```

**手把手练一次冲突**（刻意制造）：

```bash
git switch -c feature/a
echo "A 版本" >> notes.md && git commit -am "a"
git switch main
echo "B 版本" >> notes.md && git commit -am "b"
git merge feature/a
# → 冲突！ notes.md 里有 <<<<<<< HEAD
```

**学会读冲突标记**：

```
<<<<<<< HEAD              你当前所在分支这一边
||||||| e274f4f           共同祖先（base）—— diff3/zdiff3 风格才有
=======                   分界线
>>>>>>> feature/a         正在合进来的那一支
```

> 💡 **本机 `merge.conflictStyle = zdiff3`** ⇒ 比默认多一行 base，
> 能看出"两边各自改了什么"，比只看两边好判断。

**★ 三步解决（第三步最常漏）**：

```bash
# 1. 手动改文件，删掉标记，保留最终要的文本
#    ⚠️ 多数时候答案是"两边都要"（互补的两句话），不是"选一边"
# 2. git add <file>        ← 这一步是"我标记为已解决"的信号
# 3. git commit            ← 解决冲突必须先 add，否则提交会被拒
```

**状态列的含义**：`UU` = 两边都冲突未解决 → `git add` 后变 `M ` = 已暂存待提交。

**三个"全身而退"的工具**：

| 命令 | 作用 |
|---|---|
| `git merge --abort` | ★ 放弃整个合并，回到合并前（比手动 reset 安全） |
| `git checkout --ours <file>` | 只保留你当前分支那一版（按文件） |
| `git checkout --theirs <file>` | 只保留对方那一版（按文件） |

> ⚠️ `--ours/--theirs` 是**相对你站在哪个分支**的 —— 从对面合过来时正好反过来，
> 容易搞混。而且手边几乎总是"两边都要"。

**★ "独占时 vs 共享时"（本周最重要的一条）**：

| 操作 | 独占（本地、没推、没别人拉过） | 共享（远端分支、别人拉过） |
|---|---|---|
| `git reset --hard` | ✅ 安全 | ❌ 会毁掉别人的分支 |
| `git merge` 直接合 | ✅ 可以 | ⚠️ 应走 PR，留审阅点 |
| `git commit --amend` | ✅ 可以 | ❌ 会改掉别人已拉的提交 |

⇒ **规则不是教条，是由"有没有别人依赖这段历史"决定的。**

### 任务 3.3 · 加一个 CI 自动发布（1 小时）★ 呼应第 4 周

```yaml
# .github/workflows/pages.yml
name: deploy pages
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: '3.12'}
      - run: pip install mkdocs mkdocs-material
      - run: mkdocs build --strict
      - uses: actions/upload-pages-artifact@v3
        with: {path: site}
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: github-pages
    steps:
      - uses: actions/deploy-pages@v4
```

**验收**：`git push` 之后 2 分钟，你的笔记站更新了。

> 💡 **这就是爬爬虾讲 GitHub Actions 的实际价值**：
> 不写服务器、不装环境、不用手动 rsync —— 推代码，站点自己更新。

### 任务 4.3 · 把校内三台机管起来（3 小时）

你有 `ops\farm-status.ps1`（三机 GPU 池状态汇总）、`ops\gpu-lease.ps1`（按需租约）
和 `ops72.py`（**72 小时预算闸**）。
**这几个脚本本身就是 GitHub Actions 的绝佳素材**：

```yaml
# 每天早上把三机状态贴到仓库的 README 或一个 issue
name: daily farm status
on:
  schedule: [{cron: '0 7 * * *'}]
  workflow_dispatch:
jobs:
  status:
    runs-on: windows-latest        # 这些脚本是 PowerShell + ssh
    steps:
      - uses: actions/checkout@v4
      - name: farm status
        run: ./ops/farm-status.ps1 -Json > farm-status.json
      - name: commit
        run: |
          git config user.name  "ci"
          git config user.email "ci@local"
          git add farm-status.json
          git diff --staged --quiet || git commit -m "chore: 每日 GPU 池状态"
          git push
```

> ⚠️ **必须先读 `ops\README.md` 的纪律再动手**：
> `gpu-lease.ps1` 的设计原则是**只读别人的资源、不 kill、不改、不读别人的私有日志**，
> 且 `RESOURCE_POLICY: no_scheduled_automation=true`。
> **把它搬到 GitHub Actions 上跑定时任务，和这条纪律是冲突的** ——
> 正确做法是**定时只做只读状态汇总**，不要自动申请租约。

> 💡 **顺带把 72h 预算闸也接上**：`ops72.py <PLAN.json>` 判定某个实验会不会超 72 小时
> （内建 ×1.25 安全系数、最少 100 个样本、拒绝猜）。
> **它是"只读 + 纯计算"，放进 CI 完全不违反上面的纪律**，
> 而且比"人记得看"可靠得多。

### 任务 5.1 · 读懂 skill 的三层结构（2 小时）

```
my-skill/
├── SKILL.md          ← 必需。frontmatter（name/description）+ 正文指令
├── references/       ← 可选。细节文档，按需被 agent 读
├── scripts/          ← 可选。可执行脚本
└── assets/           ← 可选。模板/图片等
```

**本机已有大量现成样本**，直接读：

```bash
ls ~/.claude/skills/ | head -20
cat ~/.claude/skills/<某个你用过的>/SKILL.md | head -40
```

**手把手拆解 frontmatter**：

```yaml
---
name: relay-switch          # kebab-case，和目录名一致
description: 切换中转站并保留旧对话的连续性。当用户说"换站/额度用完/切到 AgentRouter"时使用。
---
```

> ⭐ **`description` 是唯一决定"会不会被触发"的东西**。
> 写得含糊，agent 就永远不调用它 —— 这是自写 skill 最常见的失败原因。
> **写成"什么时候用"的句式，而不是"这是什么"的句式。**

## 第 6 周 · B2 · CLI + Skill 浏览器自动化（8 小时）

**爬爬虾主线**：《CLI + Skill 搭建浏览器 AI 自动化框架》
（用 `playwright-cli install --skills` + skills **取代 MCP**）

### 任务 6.1 · 理解"为什么用 skill 取代 MCP"（1.5 小时）

| | MCP | CLI + Skill |
|---|---|---|
| 接入方式 | 配置文件里加 server | 一个 CLI + 一个 skill |
| 权限 | 常驻进程 | 按需拉起 |
| 可读性 | 要读 MCP 文档 | **skill 就是 markdown，agent 直接读** |
| 跨 agent | 要各自实现 | **同一份 skill，两个 agent 都能用** |

### 任务 6.2 · 装 playwright-cli 并生成 skill（2.5 小时）

```bash
playwright-cli install --skills
# 生成到你的 skills 目录
```

**手把手试一次**（B站登录态持久化是重点）：

```bash
playwright-cli --persistent open https://www.bilibili.com
# 在弹出的浏览器里登录一次
playwright-cli --persistent snapshot     # 页面结构快照给 agent 看
playwright-cli --persistent click "登录"
```

> ⭐ **`--persistent` 是这套方案的灵魂**：登录态存在磁盘上，
> 下次 agent 直接复用，不用重新扫码。**这也正好解决"每天自动签到"的问题**
> —— 你的 All API Hub 扩展做的是同一件事，只是实现路径不同。

### 任务 6.3 · 给你现有的签到流程写一个 skill（4 小时）

**你有两条签到路线**：
- All API Hub 扩展（浏览器里跑，依赖 Chrome 开着）
- CLI + playwright skill（本机跑，`--persistent` 保登录态）

**写一个 `relay-checkin` skill**，把后者做出来：

```
~/.claude/skills/relay-checkin/
├── SKILL.md
├── references/sites.md      ← 各站登录 URL + 签到按钮位置
└── scripts/checkin.py       ← 调 playwright-cli
```

**scripts/checkin.py 的骨架**：

```python
import json, subprocess, pathlib

SITES = json.loads((pathlib.Path(__file__).parent.parent / 'references' / 'sites.json').read_text())

def checkin(site):
    # 每个站的签到是"打开页面 → 点按钮 → 确认余额变了"
    for step in site['steps']:
        subprocess.run(['playwright-cli', '--persistent', *step], check=False)

if __name__ == '__main__':
    for s in SITES:
        checkin(s)
```

**验收**：跑一次，20 个站的余额截图/日志都回来了。

### 任务 7.2 · 两个 agent 分工改同一个仓库（3 小时）

**手把手（这是本课的核心实验）**：

```bash
# agent A（Claude Code）：改文档
git switch -c agent-a/docs
# agent B（Codex）：改脚本
git switch -c agent-b/scripts
```

两个 agent **在两个分支上并行**（同机跑要注意 app-server 独占 → 串行启动）：

```
给 Claude Code: "在 agent-a/docs 分支上，把 15.5 那节的模型表按最新实测数据更新"
给 Codex:        "在 agent-b/scripts 分支上，给 verify.py 加一个 --json 输出模式"
```

**合并**（你来）：

```bash
git switch main
git merge agent-a/docs
git merge agent-b/scripts
# 如果两个 agent 改了同一处 → 手动解冲突，这正是要练的
```

**验收**：合并后 `verify.py --json` 能跑，且手册里的表和脚本行为一致。

## 三条纪律（学 Agent 编程最容易违反的）

1. **合并权留给人。** agent 可以在分支上提交、可以提 PR，**但不许自己 merge 到 main**。
2. **凡是要提交的，先想"这个文件里有没有 secret"。** `.env`、`*credentials*.json`、
   `auth.json` 一律 `.gitignore`。**先写 .gitignore，再 git add。**
3. **不用的技能等于没学。** 每周末必须在自己的真实项目上用一次这周学的东西。
