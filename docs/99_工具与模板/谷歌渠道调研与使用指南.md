## 3. 使用指南

### 3.1 第一步：拿一个 AI Studio 的 key

> ★ **先看本节末尾的「本机实测」** —— 这台机器的出口地区有个坑，
> 不先解决的话，key 拿到了也会被拒。

1. 打开 <https://aistudio.google.com/apikey>（土耳其区账号正常）
2. 确认**账号国家/地区是土耳其**（Google 账号 → 个人信息 → 国家/地区）
3. Create API key → 选一个 Google Cloud 项目（**额度按项目算**，所以建一个专门的项目）
4. 复制 key（2026-05-28 后的 key 是 auth key，正常用就行）
5. **立刻验证**（这一步能同时验出"区域不被支持"和"key 无效"两种问题）：

```bash
curl -s "https://generativelanguage.googleapis.com/v1beta/models?key=<KEY>" | head -c 400
```
- 返回模型列表 ⇒ ✅ 成功
- `User location is not supported` ⇒ **IP 所在地区不支持**（换出口）
- `API key not valid` ⇒ key 或项目有问题

> 💡 **本机能到达 Google**（实测 403 = 网络通、未鉴权），
> 但**"到达"≠"能用"** —— 能不能用取决于**出口 IP 所在国家**，
> 香港不在 Gemini API 的支持列表里。解法见下面的「本机实测」。

---

#### ★ 本机实测（2026-11-12）：**出口其实是好的，不用改任何东西**

一开始我以为"香港出口 = 死路"，**这是错的**。用 Clash 的路由日志一查就清楚了：

| 项 | 实测值 |
|---|---|
| 本机代理 | **Clash Verge**（verge-mihomo），系统代理 `127.0.0.1:7897`，模式 rule，**TUN 模式开着** |
| 通用出口 IP（`ifconfig.co` 等非 Google 域名） | `220.246.52.52`（**HKT 香港**） |
| **Google API 的出口**（`generativelanguage.googleapis.com` / `cloudcode-pa.googleapis.com`） | **日本** —— Clash 日志：`match RuleSet(gemini) using 📢 谷歌服务[【3x】中转|日本樱花🇯🇵]` |
| 日本在 Gemini API 支持列表里？ | **✅ 在** |
| 当前激活订阅 | `RcqySQpe7uyY`（146 节点） |
| 生效的 Google 分流 | ① `DomainSuffix(googleapis.com) → 📢 谷歌服务` ② `RuleSet(gemini)`（blackmatrix7，含 `generativelanguage` 关键字） |

⇒ **结论：Google 的 API 调用本来就走日本出口，地区不构成阻塞。**
> ⚠️ **为什么"看起来像香港"**：用 `ifconfig.co` 查 IP 走的是**通用分流**（香港），
> 而 Google 的域名走**专用分流**（日本）。
> **拿通用出口 IP 去判断 Google 的地区可行性，会得出错误结论** ——
> 要看的是 **Google 域名的实际出口**，也就是 Clash 日志里 `using` 后面那个节点。

⇒ **你要做的只有两件**：
1. **AI Studio 页面建 key**（<https://aistudio.google.com/apikey>）——
   登录和建 key 走通用分流（香港），**香港不影响这两步**。
2. **命令行不用设代理** —— TUN 模式开着，`curl` / `dispatch.py` / `gemini` 的流量
   **自动被 Clash 接管并按同一套规则分流**。
   （实测：`generativelanguage.googleapis.com` 的连接记录里同时出现
   `198.18.0.1` ← TUN 假 IP 和 `127.0.0.1` ← 显式代理，两条都走日本。）
   ⇒ **`HTTPS_PROXY` 是可选的**，设了也无害，但**不是必需**。

> 💡 **万一哪天这个日本节点挂了**：Clash 日志里会出现
> `level=warning ... dial 📢 谷歌服务 ... error: hn6vn2.ai00.de:443 connect e...`
> 这时再去 GUI 里把 `📢 谷歌服务` 换成 `🇯🇵 日本节点` / `🇺🇸 美国节点`。
> ⚠️ **Clash 的外部控制器是关的**（`enable_external_controller: false`），
> 所以**换节点必须你在 GUI 里点**，我没法脚本切。
> 想让我以后能自动切，就在 Verge 设置里打开「外部控制器」。

> 💡 **另一个订阅里还有土耳其节点**：`Rd1KalmmTmnK.yaml` 有 `土耳其TR-A`，
> 激活它就有土耳其出口（不过日本已经够用，不折腾）。

### 3.2 第二步：把 Gemini 接进 Claude Code

Claude Code 说 **Anthropic Messages API**；**Google 没有 Anthropic 兼容端点** ⇒ 必须有翻译层。

**方案 A：Claude Code Router**（最通用）
- 把 Claude Code 的请求重定向到 Gemini/DeepSeek/Qwen 等
- 保留 Claude Code 的界面（CLI、IDE 插件、模型选择器、工具调用），换掉后端模型
- 要求 Node.js 18+
- 配置在 `~/.claude-code-router/config.json`

**方案 B：gemini-cli-proxy**（社区，开源）
- 把 Gemini Code Assist / Gemini CLI 包成 **OpenAI + Anthropic 双兼容 API**
- **自动复用 Gemini CLI 的 OAuth 凭据**（不用自己申请 key）
- 支持 Gemini 3 Pro/Flash、**原生 thinking 块**、**限流自动降级**、Google Search grounding
- 模型别名形如 `gemini-3-pro-high[1m]`
- <https://github.com/emrullahakclk/gemini-cli-proxy>

**方案 C：最简 —— 直接改环境变量**
```bash
# Claude Code
set ANTHROPIC_BASE_URL=<指向代理>
set ANTHROPIC_AUTH_TOKEN=<key>
```
（Google 本身没有 Anthropic 面，所以这里仍要先有代理。）

**方案 D：自建本地代理**（推荐给你）
- 多 key Gemini failover + 本地零延迟回退
- 专门解决 429 / 配额耗尽导致 Claude Code 中断

### 3.3 第三步：把 Gemini 接进 Codex —— **不能直接接**

**原因（硬性）**：
1. Codex **≥ 0.94.0 已移除 `wire_api = "chat"`**，只说 **Responses API**。
   你的本机是 **codex 0.163.0** ⇒ 只支持 `wire_api = "responses"`。
2. Google 的 OpenAI 兼容层 **没有 `/responses` 端点**。
   官方文档列出的只有：`/chat/completions`、`/embeddings`、`/images/generations`、
   `/videos`（部分）、`/batches`（部分）、`/models`。
   Google 自己的说法是"We will initially support the Chat Completions API and Embeddings API"。
3. ⇒ **必须在前面插一个 Responses → Chat Completions 的翻译代理**
   （krouter / Portkey / 自建），让 Codex 说 Responses、代理负责降级。

**错误对照**：

| 报错 | 原因 |
|---|---|
| `Error loading config.toml: 'wire_api = "chat"' is no longer supported.` | Codex 版本太新 ⇒ 只能 `responses` |
| 404 | 上游没有 `/responses` 路由 ⇒ 需要翻译代理 |
| 400 | 模型名不在白名单 |
| 401 | key 无效或没这个模型的权限 |

### 3.4 ★ 第四步：接进你自己的架构（**最贴合你现状的一条路**）

你的 `claude_gateway_bridge.py` 现在是这样的：

```python
use_responses = bool(body.get('tools'))
if use_responses:
    wire_body, name_map = convert_request(body, UPSTREAM_MODEL)   # ← Anthropic → Responses
wire_path = '/v1/responses' if use_responses else self.path
req = urllib.request.Request(CONFIG['base_url'].rstrip('/') + wire_path, ...)
```

**它已经有一个 `use_responses` 开关了** —— 带工具的 agent 请求走 `/v1/responses`，
不带工具的走原路径。

⇒ **要让桥指向 Google，需要加第三种上游协议：`chat`。**
改动范围是清楚的（`responses_adapter.py` 里三个函数）：

| 函数 | 现在 | 加 chat 模式要改成 |
|---|---|---|
| `convert_request` | 产 **Responses** 形状（`input_text`/`output_text`/`input_image`/`items`） | 产 **Chat** 形状（`messages`/`role`/`content`/`tools[].function`） |
| `convert_response` | 解析 Responses 的 `output[]` | 解析 Chat 的 `choices[0].message` |
| `stream_response` | 解析 Responses 的 SSE 事件 | 解析 Chat 的 `choices[0].delta` |

**这是个有界的改动**（一个文件、三个函数），而且**改完之后 Google 就成了网关适配器的一等上游**，
和 agentrouter/pincar 并列。

> ⭐ **这条路的价值**：Claude Code → 你的桥（18146）→ Google，
> **中间这层本来就是你自己的**，所以
> ① 不用依赖第三方代理项目 ② 你能控制降级/重试/多 key failover ③ 能把 Gemini 的
> `thinking_config`、`google_search` grounding 用 `extra_body` 透传下去。

## 4. Google 的 OpenAI 兼容层到底支持什么（实测文档口径）

Base URL：`https://generativelanguage.googleapis.com/v1beta/openai/`

| 端点 | 支持 | 说明 |
|---|---|---|
| `/chat/completions` | ✅ | 核心：流式、function calling、图像输入、音频输入、结构化输出 |
| `/embeddings` | ✅ | `gemini-embedding-2`（多模态）、`gemini-embedding-001`（纯文本） |
| `/images/generations` | ✅ | `gemini-2.5-flash-image`、`gemini-3-pro-image-preview` |
| `/videos` | ⚠️ | Veo 3.1 于 2026-10-22 下线；`gemini-omni-1.2-flash` 视频生成在此端点不支持 |
| `/batches` | ⚠️ | 增删查可用，**上传/下载不支持**（要用 `google-genai` SDK） |
| `/models` | ✅ | list / retrieve |
| **`/responses`** | ❌ | **文档里没有** |

**thinking 参数映射**（这个对 agent 很重要）：

| OpenAI `reasoning_effort` | Gemini `thinking_level` / `thinking_budget` |
|---|---|
| `minimal` | minimal（2.5 用 thinking_budget=1024） |
| `low` | low（2.5: 1024） |
| `medium` | medium（2.5: 8192） |
| `high` | high（2.5: 24576） |

- 不指定 ⇒ 用模型默认
- `reasoning_effort="none"` 可关 thinking —— **但 Gemini 2.5 Pro 和 3 系关不掉**

**Gemini 专属能力**走 `extra_body`：
`cached_content`（内容缓存）、`thinking_config`、`safety_settings`、
`google_search`（grounding，**仅 Gemini 3 及更新**）、`generation_config`、`aspect_ratio`。

## 5. 作为主力 AGENT 是否可行 —— 分三层看

### 5.1 ❌ **Codex 的主力：不可行（协议层面）**

| 障碍 | 事实 |
|---|---|
| Codex 只说 Responses | ≥0.94 移除 `wire_api="chat"`，你本机 0.163 |
| Google 没有 `/responses` | 官方文档只列 chat/completions 等 |
| 翻译代理会丢保真度 | Codex 的 agent loop 依赖 Responses 的 `previous_response_id`、多轮状态、事件类型 |

⇒ **要做成 Codex 主力，必须先有一个翻译代理**（krouter / Portkey / 自建）。
在你自己的 `claude_gateway_bridge.py` 里加 chat 模式也算一个（但它现在是 Anthropic 入口）。

### 5.2 ⚠️ **Claude Code 的主力：可行，但要走代理，质量打折**

- 社区实测共识：**第三方 provider 下「最难的自主重构」仍不及真 Claude 模型**。
  工具调用语义、diff 应用、多轮长上下文的稳定性，Anthropic 形状 → Gemini 形状的翻译会损耗。
- **适合当什么**：大批量、机械性的活（读代码、生成样板、写测试、批量蒸馏课程）
- **不适合当什么**：需要精确遵守你仓库纪律的多文件重构 —— 你自己写的 `AGENTS.md`
  里那三条纪律，靠的就是指令遵从度。

> ⭐ **对你这台机器的具体判断**：
> 你的 `dispatch.py` 蒸馏流水线（跑一个任务文件 → 出一课）**正好是机械性大批量活** ⇒
> Google 适合当**蒸馏流水线的批处理后端**，不适合当交互主力。

### 5.3 ✅ **最强路径：直接用 Google 自己的 agent 当主力**

如果"主力 AGENT"指的是"我日常主要用它干活"，那最合理的不是"把 Gemini 塞进 Claude Code"，
而是**直接用 Antigravity / Gemini CLI**：

| | 优点 | 代价 |
|---|---|---|
| **Antigravity CLI/IDE** | ① 官方 2026 主推 ② agent-first，支持并行多个 agent ③ 有浏览器控制 ④ 随 AI Pro/Plus 订阅 | ① 额度绑订阅 ② 土区账号可能遇到"不 eligible" ③ $10 GCP credit 的说法**只来自社区帖，未经官方文档证实** |
| **Gemini CLI + 自带 key** | ① Apache-2.0 开源 ② 直接用 AI Studio 免费额度 ③ 本机网络已通 ④ 想写 skill/脚本完全自由 | 个人免费登录通道已关，只能走 API key 额度 |

## 6. 怎么接进你现有的体系

### 6.1 给统一换站器加一个 `google` 选项

`relay_sites.json` 里加一个站，**并且把"为什么不能直接用"写进去**
（这是你那张表的真正价值 —— 让人一眼看出该走哪条路）。

但先说清楚：**Google 目前不能接进 Codex 那一层**，所以它属于"网关适配器"这一腿：

```
Claude Code ──→ 你的桥 (18146) ──→ agentrouter / pincar / google(待加 chat 模式)
Codex       ──→ 走 Codex 原生       ──→ agentrouter / pincar
```

⇒ **Google 是网关适配器的第三个上游，不是 Codex 的第四个站。**

### 6.2 让 `dispatch.py` 多一个后端（**性价比最高的一条，已实现**）

> ⚠️ **先纠正一个差点写错的地方**：我最初以为 `dispatch.py` 走 OpenAI SDK 的
> `chat.completions`，所以"加个 site 条目零改动"。
> **实际查了源码：它走的是 `codex exec --profile X`** ——
> 因为中转站**校验客户端指纹**（pincar 对普通 HTTP 客户端返 403）。
> **所以"Google 直接塞进现有 SITES 列表"是不行的。**

**正解：给每个站加一个 `transport` 字段** —— 这也正好对上各站的实际差异：

| 站 | 要不要官方客户端 | 走哪条腿 |
|---|---|---|
| agentrouter / pincar | **要**（指纹校验） | `transport: 'codex'` → `codex exec` |
| Google Gemini | **不要** | `transport: 'http'` → OpenAI SDK 的 `chat.completions` |

**已实现的改动**（`dispatch.py`，2026-11-12）：

```python
SITES = [
    {'name': 'agentrouter', 'transport': 'codex', ...},
    {'name': 'pincar',      'transport': 'codex', ...},
    {'name': 'google',      'transport': 'http',
     'base_url': 'https://generativelanguage.googleapis.com/v1beta/openai',
     'api_key_env': 'GEMINI_API_KEY',
     'profiles': [('gemini-3.8-flash', None),
                  ('gemini-2.5-pro', None)]},
]
```

配套三处：
1. 新增 `run_http(model, base_url, prompt, api_key)` —— 走 OpenAI SDK
2. 新增 `site_ready(site)` —— **环境变量没设的站直接跳过**，
   不给每次任务白烧一个重试位
3. 故障转移循环按 `transport` 分支；`.meta.json` 记录用了哪条 transport

**现在就能验证**：
```
$ python dispatch.py --list
  3. google  https://generativelanguage.googleapis.com/v1beta/openai  transport=http
       [不可用: GEMINI_API_KEY 没设（跳过）]
```
⇒ **没 key 也不影响现有流程** —— Google 是纯粹的"第三条腿"，有 key 才生效。

**收益**：
- 课程蒸馏是**大批量机械活**（读材料 → 出五件套），正是 Gemini 的甜区
- 额度独立 ⇒ **中转站 402/429 时还有第三条腿**（这正是 `dispatch.py` 存在的意义）
- 成本低：免费层 250~1,000 次/天；蒸馏一课要几次到几十次
- **不占 Codex 的配额** —— 这对 72 小时闸下的批量任务很重要

⚠️ **前提**：需要 `openai` 这个 pip 包（`pip install openai`），
以及一个 **AI Studio 的 key**（§3.1）。

> ⭐ **为什么这条比"给 Claude Code 插代理"更值得做**：
> Claude Code 插代理是**交互质量**的赌注（协议翻译会掉保真度）；
> 而给 `dispatch.py` 加后端是**纯增量**（多一条腿，不动现有两条）。
> **同样的 key，后者 ROI 高得多。**
